Quattro risposte alla stessa proposta

Immagina questa chiamata: PublishAnnouncement(channel: "evento", message: "Benvenuti!"). Il tool è avvolto in ApprovalRequiredAIFunction: prima di eseguirlo serve un’autorizzazione. La scelta umana può avere una durata diversa.

Scelta in D8Cosa autorizzaAlla prossima chiamata
N · RifiutaQuesta chiamata non esegue.Una nuova proposta richiede una nuova decisione. Il rifiuto non crea una blacklist permanente.
S · Una voltaSolo la chiamata mostrata.Chiede ancora, anche con argomenti identici.
A · Stessi argomentiQuesta chiamata e quelle identiche nella sessione.Stesso tool, stesso canale, stesso testo: passa. Cambia anche un solo argomento: chiede.
T · Tutto il toolQuesta chiamata e le successive allo stesso tool nella sessione.Passa anche con testo o canale diversi. Il consenso ha una portata più ampia.
AIContent answer = choice switch
{
    "s" => request.CreateResponse(true),
    "a" => request.CreateAlwaysApproveToolWithArgumentsResponse(),
    "t" => request.CreateAlwaysApproveToolResponse(),
    _   => request.CreateResponse(false)
};

await agent.RunAsync(
    new ChatMessage(ChatRole.User, [answer]), session);
La sessione è la memoria dei consensi.

Riutilizza lo stesso AgentSession tra i turni. D8 mantiene questa sessione finché digiti /reset o chiudi la console. CreateResponse lega la decisione alla richiesta originale; il binding dell’harness mantiene nome e argomenti approvati.

02 /

AutoApprovalRules, passo per passo

Una regola è una funzione C# scritta dall’applicazione. Risponde a una domanda: “Posso autorizzare automaticamente questa chiamata?”

Il modello propone tool e argomenti. Il codice della regola li esamina tramite ToolAutoApprovalRuleContext, che espone anche agente, sessione, messaggi della richiesta e opzioni del run. Il risultato è un ValueTask<bool>; può quindi usare anche una verifica asincrona. In D8 basta un confronto locale.

private static ValueTask<bool> ApproveDrafts(
    ToolAutoApprovalRuleContext context)
{
    var call = context.FunctionCallContent;
    bool match =
        call.Name == "PublishAnnouncement" &&
        call.Arguments?.TryGetValue(
            "channel", out var channel) == true &&
        channel?.ToString() == "bozze";

    return ValueTask.FromResult(match);
}
true → autorizza

Il tool e il canale corrispondono: l’harness approva senza mostrare un prompt umano e non valuta le regole successive.

false → prosegui

Questa regola non autorizza. L’harness prova la successiva; se nessuna restituisce true, restituisce la richiesta all’applicazione per far decidere la persona.

  1. Consenso ricordato?Se una standing approval corrisponde, la chiamata è già autorizzata.
  2. Regola 1, 2, 3…In ordine di registrazione. Si ferma al primo true.
  3. Nessun consenso?La richiesta arriva alla UI: approva o rifiuta.
  4. RipresaIl risultato del tool, oppure il rifiuto, torna nel flusso dell’agente.

Due regole: è sufficiente un sì

Regola 1: “approva il canale bozze”. Regola 2: “approva il testo esatto Benvenuti!”. Per evento / Benvenuti!, la prima restituisce false, la seconda true: il tool esegue.

Non serve che tutte siano vere. Per richiedere due condizioni insieme, uniscile con && nella stessa regola e considera anche eventuali altre regole e consensi ricordati.

Chi decide la regola?

La configuri tu in HarnessAgentOptions.ToolApprovalAgentOptions.AutoApprovalRules. La scelta “ricorda” arriva invece da una risposta umana precedente.

La regola viene rivalutata sulle nuove chiamate che non hanno già un consenso ricordato. /reset azzera i consensi della sessione; la configurazione --auto resta attiva.

DisableToolAutoApproval = false,
ToolApprovalAgentOptions = new()
{
    AutoApprovalRules = [ApproveDrafts],
    MaxAutoApprovalIterations = 3
}
Un limite obbligatorio deve essere applicato prima dell’effetto.

false non blocca: un’altra regola, un consenso ricordato o una persona possono autorizzare. Se “mai oltre 99 euro” è una policy, il tool o il servizio deve verificarla anche dopo l’approvazione. Inoltre, un consenso “tutto il tool” viene controllato prima di AutoApprovalRules.

Il nome DisableToolAutoApproval può confondere

false è il default: include ToolApprovalAgent, con gestione dei consensi ricordati, code e regole. Senza regole configurate e senza consensi precedenti, i tool marcati continuano a chiedere.

true rimuove quel middleware. Un tool avvolto in ApprovalRequiredAIFunction mantiene il requisito di approvazione. In D8 lasciamo false e usiamo --auto solo per aggiungere la callback.

Ci sono più richieste o troppe continuazioni automatiche?

L’harness gestisce una coda per raccogliere le decisioni sulle richieste. L’applicazione deve continuare a controllare le richieste di approvazione dopo ogni run. MaxAutoApprovalIterations limita le reinvocazioni automatiche nello stesso run: al limite, eventuali richieste ancora da approvare tornano alla persona. D8 limita separatamente anche i passaggi manuali.

Riferimenti: contratto di AutoApprovalRules · ordine di valutazione e stato della sessione.

    Prova 3 · Una regola false non è un rifiuto
    Nuova sessione. Attiva solo SoloBozze, seleziona evento e proponi. La regola restituisce false e puoi ancora approvare con S. Con bozze, la stessa regola approva automaticamente.
    

    Prova 4 · La seconda regola può dare il via
    Nuova sessione. Attiva entrambe le regole, scegli evento e testo Benvenuti!. Osserva: SoloBozze → false; SoloBenvenuti → true; esecuzione senza domanda.

    Nuova sessione, regole spente. Proponi → T. Attiva SoloBozze e riproponi sul canale evento con un testo diverso. La memoria autorizza prima della callback: SoloBozze non viene valutata.
    

    

    04 /
    HITL comprende anche il dialogo
    HARNESS · PLAN / EXECUTE
    Chiarire, rivedere, approvare un piano
    Con AgentModeProvider, la modalità plan guida l’agente a raccogliere requisiti e proporre il lavoro. La persona può rispondere “usa il canale interno” o “cambia il secondo passo”. L’app può passare a execute con SetModeAsync.
    La conferma del cambio modalità è un comportamento guidato dalle istruzioni. I tool di modalità e todo non richiedono di per sé approvazione. Gli effetti che devono avere un consenso esplicito vanno protetti sul tool.
    Il sample PlanningOutputObserver usa JSON strutturato per distinguere Clarification e Approval, poi presenta domande e scelte. È codice di interfaccia del sample da integrare, non una UI fornita automaticamente dal costruttore dell’harness.
    Planning e todo · PlanningOutputObserver
    

    WORKFLOWS · RICHIESTA / RISPOSTA
    Fermarsi per ricevere un dato o una revisione
    Un workflow può inviare una richiesta tipizzata tramite RequestPort. L’app riceve un RequestInfoEvent, mostra il contenuto alla persona e restituisce la risposta con SendResponseAsync.
    La risposta può essere un’approvazione, una scelta, un numero o un testo corretto. Il workflow riprende il percorso previsto. I checkpoint permettono di conservare lo stato per la ripresa.
    È adatto a più passaggi di revisione o attese esterne. La raccolta dell’input e la persistenza vanno collegate all’applicazione. Nelle orchestrazioni, anche l’approvazione di un tool può essere veicolata da questo meccanismo.
    HITL nei workflow
    

    Scegli il punto della decisione.
    Per autorizzare una chiamata usa l’approvazione tool. Per definire cosa fare usa il dialogo di pianificazione. Per raccogliere una risposta in una sequenza di lavoro usa una richiesta del workflow. D8 si concentra sulle approvazioni tool dell’harness.

    dotnet run --project D8.HumanInTheLoop --no-build -- --auto
    1. Incolla Pubblica sul canale bozze il testo esatto: Prova microfono.
    2. La console mostra SoloBozze = True: il tool esegue.
    3. Ripeti con canale evento.
